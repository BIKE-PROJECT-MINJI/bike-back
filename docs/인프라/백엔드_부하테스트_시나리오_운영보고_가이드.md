# 백엔드 부하테스트 시나리오와 운영 보고 가이드

## 목적

이 문서는 개발자가 아니어도 BIKE 백엔드 부하테스트 결과를 읽을 수 있게 만드는 기준 문서다.
핵심 질문은 아래 세 가지다.

- 사용자가 동시에 몰려도 앱이 느려지지 않는가?
- 느려졌다면 어느 API 또는 내부 로직이 원인인가?
- 주행 기록 저장, 후처리 큐, DB/Redis/외부 API가 꼬이지 않는가?

## 공통 관측 기준

부하테스트 중에는 모든 요청과 내부 로직을 메트릭으로 기록한다.
단, 로그는 전부 남기지 않는다. 빠른 정상 요청까지 모두 로그로 쓰면 부하테스트 자체가 디스크 IO를 압박할 수 있기 때문이다.

기본 로그 정책은 아래다.

- HTTP 요청 로그: 실패, 4xx/5xx, 또는 500ms 이상 느린 요청만 남긴다.
- 내부 operation 로그: 실패 또는 200ms 이상 느린 내부 로직만 남긴다.
- 메트릭: 빠른 요청과 느린 요청 모두 100% 기록한다.

즉 “숫자 기반 성능 분석”은 빠지지 않고, “사람이 읽을 로그”만 줄인다.

DB가 꽉 찬 상황은 별도 신호로 본다.

- `hikaricp_connections_active`가 `hikaricp_connections_max`에 붙어 있고 `idle=0`이면 DB 커넥션 풀이 꽉 찬 상태다.
- `hikaricp_connections_pending`이 증가하면 요청들이 DB 커넥션을 기다리며 줄을 선 상태다.
- `bike_database_backpressure_rejected_total`이 증가하면 서버가 30초씩 붙잡는 대신 빠르게 503으로 거절했다는 뜻이다.

이 503은 “기능 버그”라기보다 “현재 인프라/DB 처리량보다 요청이 많다”는 보호 신호다.
이 신호가 보이면 VU를 더 올리지 않고 DB pool 크기, DB 인스턴스, write 동시성, finalization worker 설정을 같이 본다.

## 시나리오 1. Smoke

짧은 예행연습이다.

사용자 상황:

- 앱이 서버에 붙는지 확인한다.
- 홈 화면 코스 목록을 본다.
- 대표 코스 상세와 경로 포인트를 읽는다.
- 주행 전 위치 판정을 한 번 호출한다.

확인하려는 문제:

- API 경로가 깨졌는지
- 인증/환경변수/코스 ID 탐색이 실패하는지
- 부하테스트 스크립트 자체가 잘못됐는지

## 시나리오 2. Baseline

평소 사용량을 가정한 테스트다.

사용자 상황:

- 일부 사용자는 홈에서 코스를 둘러본다.
- 일부 사용자는 코스를 고르고 경로를 확인한다.
- 일부 사용자는 주행 중 HUD 판정을 계속 요청한다.
- 인증이 켜져 있으면 내 활동 요약과 최근 위치도 함께 본다.

확인하려는 문제:

- 일반적인 혼합 사용에서 p95 응답시간이 안정적인지
- DB 커넥션 풀이 차오르지 않는지
- route snapshot cache가 의도대로 동작하는지
- 외부 provider 호출이 전체 응답을 늦추지 않는지

## 시나리오 3. Stress

평소보다 높은 사용량을 짧게 올리는 테스트다.

사용자 상황:

- 많은 사용자가 동시에 코스 목록, 지도 경로, 주행 판정을 요청한다.
- 정상 사용량보다 높은 상태에서 어디부터 느려지는지 확인한다.

확인하려는 문제:

- p95/p99가 급격히 올라가는 지점
- 5xx 또는 timeout이 생기는 지점
- Hikari pending connection 증가
- Redis/provider 장애가 전체 API로 번지는지

## 시나리오 4. Burst

여러 사용자가 거의 동시에 “주행 시작/주행 기록 저장/주행 중 판정”을 누르는 상황이다.

사용자 상황:

- 여러 명이 동시에 주행 기록을 저장한다.
- 저장된 기록은 finalization worker가 후처리한다.
- 동시에 다른 사용자는 주행 중 HUD 판정을 계속 요청한다.

확인하려는 문제:

- DB insert와 후처리 job이 쌓이는지
- 같은 job을 중복 처리하지 않는지
- finalization pending/running/failed가 계속 증가하지 않는지
- 주행 기록 저장 API는 성공했지만 후처리가 밀리는지
- route point 수가 많을 때 IO와 DB lock이 튀는지

2026-06-27 AWS burst 관측에서 확인된 대표 실패는 아래다.

- 25 VU 혼합 burst에서 전체 p95가 약 30초까지 상승했다.
- app log에 `HikariPool-1 - Connection is not available, request timed out after 30000ms`가 반복됐다.
- `total=10, active=10, idle=0, waiting=20+` 상태라 DB pool이 먼저 포화됐다.
- finalization job은 테스트 종료 시 pending/running/failed가 0이었으므로 1차 원인은 job backlog보다 DB connection starvation으로 본다.

따라서 burst는 “한 번에 크게 때리기”보다 작은 단계로 올리며, DB pool 포화 신호가 보이면 즉시 멈춘다.

권장 시작값:

```bash
BASE_URL=http://localhost:8080 \
MANAGEMENT_URL=http://localhost:18081 \
SCENARIO=burst \
PERSONAS=write,inRide,preRide \
AUTH_AUTO_REGISTER=true \
ENABLE_WEATHER_READ=false \
BURST_WRITE_VUS=10 \
BURST_WRITE_ITERATIONS=20 \
WRITE_ROUTE_POINT_COUNT=120 \
WRITE_POLL_FINALIZATION=true \
ops/loadtest/run-diagnostic-k6.sh
```

## 결과 보고서 읽는 법

`ops/loadtest/run-diagnostic-k6.sh`를 쓰면 아래 파일이 생성된다.

- `<TEST_ID>-summary.json`: k6 원본 요약
- `<TEST_ID>-stdout.log`: 느린 요청 샘플과 k6 로그
- `<TEST_ID>-prometheus-after.txt`: 테스트 직후 Prometheus metric
- `<TEST_ID>-readable-report.md`: 사람이 읽는 요약 보고서

보고서에서 먼저 볼 것은 아래 순서다.

1. 실패율
2. 체크 성공률
3. API별 p95
4. 내부 로직별 p95 근사값
5. 느린 요청 샘플의 request_id / trace_id

## 병목 판단 기준

API p95와 내부 operation p95가 같이 높으면 해당 내부 로직이 1차 병목 후보다.

예:

- `course-read`가 느리고 `course.read.list`도 느리다: 코스 목록 조회 쿼리나 route snapshot 조립을 본다.
- `ride-policy`가 느리고 `course.route.snapshot`이 느리다: 경로 캐시 miss, route point 로딩, projection 계산을 본다.
- `write-core`는 빠른데 `write-finalization`이 느리다: 저장 API보다 후처리 worker와 DB job queue를 본다.
- API는 느린데 내부 operation은 낮다: 인증 필터, JSON 직렬화, 네트워크, 커넥션 대기를 본다.
- API와 operation이 둘 다 30초 근처에서 실패한다: Hikari connection timeout 가능성을 먼저 본다.

## 개선 우선순위

1. Hikari pending 또는 DB backpressure rejection이 보이면 VU 증가를 중단한다.
2. request_id / trace_id 샘플로 어느 API가 DB connection을 기다렸는지 확인한다.
3. `ride.record.save_full`, `ride.policy.evaluate`, `location.recent.find`처럼 쓰기/주행 중 핵심 operation의 p95를 비교한다.
4. finalization job pending/running/failed가 늘지 않으면 worker backlog보다 DB pool/DB 인스턴스 처리량을 먼저 본다.
5. DB 인스턴스 분리, Hikari pool 조정, worker batch/poll 조정은 한 번에 섞지 않고 한 변수씩 바꿔 재측정한다.

## 중단 기준

아래 상황이면 VU를 더 올리지 않는다.

- 실패율이 1%를 넘는다.
- 5xx가 연속 발생한다.
- Hikari pending connection이 지속된다.
- `bike_database_backpressure_rejected_total`이 증가한다.
- finalization job pending이 테스트 종료 후에도 계속 증가한다.
- Redis/provider timeout이 전체 API 실패로 번진다.

이 경우에는 즉시 request_id와 trace_id 샘플을 잡고, 부하를 올리는 대신 원인 분류로 전환한다.
