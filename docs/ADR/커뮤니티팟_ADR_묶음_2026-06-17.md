# 커뮤니티·팟 ADR 묶음

- 작성일: 2026-06-17
- 대상: BIKE 백엔드 커뮤니티/팟 후속 구현
- 상태: 구현 전 설계 결정 초안
- 범위: 문서/ADR 작성만 수행하며, 코드, migration, Entity, Repository, Service, Controller, 테스트는 수정하지 않는다.

## 1. ADR 묶음 목적

커뮤니티/팟 SDD 초안은 공개 Course, 복사, 좋아요, 북마크, 신고, 관리자 검토, 팟 예약 기능의 후보 정책을 제시한다. 다만 현재 백엔드 구조 조사 결과, 기존 `users`, `courses`, `course_reports`, Course 목록 read model, 인증/JWT 구조와 SDD 후보 사이에 충돌하거나 먼저 닫아야 할 설계 판단이 있다.

이 ADR 묶음의 목적은 후속 구현 프롬프트가 migration/API/Service 구현을 임의로 판단하지 않도록, blocking 결정 4가지를 먼저 고정하는 것이다.

## 2. 공통 전제

- 이 문서는 구현 지시서가 아니라 구현 전 ADR이다.
- 구현자는 이 문서를 읽고도 불명확한 API path, DTO 필드, enum 값, FK 이름이 있으면 임의 구현하지 않고 후속 결정으로 올려야 한다.
- 기존 조사 보고서 기준으로 `users.beta_access_granted`, `beta_invitation_codes`, `course_reports`, `course_list_summaries`, Course cursor 목록 구조는 재사용 후보가 있다.
- 기존 조사 보고서 기준으로 `OPS_ADMIN` roles claim 발급, `course_publications`, `course_reactions`, `course_moderations`, 팟 도메인, persistent AI rate limit은 추가 설계가 필요하다.
- 공개 Course 조회는 게스트 가능, 복사/저장/반응/신고/팟 참여는 로그인 및 beta 권한 필요를 기본 정책으로 둔다.
- 신고된 Course는 신고 접수만으로 공개 목록에서 제외하지 않는다. 관리자 숨김 상태일 때만 공개 목록에서 제외한다.
- 모든 변경은 기존 API 계약과 프론트 영향 범위를 확인한 뒤 작은 PR 단위로 나눠야 한다.

## 3. ADR-1 사용자 권한/베타/OPS_ADMIN

### 문제

현재 백엔드에는 `users.beta_access_granted`와 `beta_invitation_codes`가 존재하지만, 조사 보고서 기준으로 영속화된 일반 role 구조가 명확하지 않다. JWT parser는 `roles` claim을 읽을 수 있으나, 토큰 발급 서비스가 저장된 role을 claim으로 발급하는 구조가 닫혀 있지 않다.

커뮤니티/팟 기능은 게스트, 로그인 사용자, beta 사용자, `OPS_ADMIN`의 경계가 API마다 다르다. 특히 관리자 신고 검토와 숨김 처리는 단순 로그인과 분리된 권한이 필요하다.

### 결정

- beta 권한은 기존 `users.beta_access_granted`를 사용한다.
- beta 초대코드는 기존 `beta_invitation_codes`를 재사용하되, 후속 구현 전 발급 주체, 해시 저장 여부, 기존 가입자 redeem 정책을 별도로 확정한다.
- 관리자 권한은 `OPS_ADMIN`으로 명명한다.
- `OPS_ADMIN`은 JWT에 `ROLE_OPS_ADMIN` authority로 들어가야 한다.
- `ROLE_OPS`는 기존 health/monitor 호환 용도로만 남기고, 커뮤니티 관리자 API의 기준 권한으로 쓰지 않는다.
- 사용자 role 저장은 단일 `users.role` 컬럼보다 별도 `user_roles` 계열 테이블을 우선한다.
- access token 발급 시 저장된 role 목록을 `roles` claim으로 발급한다.
- role 변경 즉시 기존 토큰을 강제 폐기하는 기능은 MVP 범위에서 제외한다. 권한 변경 반영은 재로그인 또는 token refresh 기준으로 한다.
- 권한 경계는 다음을 기본으로 한다.
  - 게스트: 공개 Course 목록/상세 조회 가능.
  - 로그인 사용자: 기본 인증 API 이용 가능.
  - beta 사용자: Course 저장, 삭제, 공개, 복사, 좋아요, 북마크, 신고, 팟 생성/참여 가능.
  - owner: 본인 Course, 본인 publication, 본인 pot 참여 상태에 대한 변경 가능.
  - `OPS_ADMIN`: 신고 검토, publication 숨김/복구, 운영용 조회 가능.

### 대안

- `users.role` 단일 컬럼: 구현은 쉽지만, beta/운영자/추가 role 확장 시 충돌 가능성이 높다.
- JWT claim에만 role 저장: DB 감사와 권한 회수가 어렵다.
- 기존 `ROLE_OPS` 재사용: 구현은 적지만, 기존 monitor 권한과 커뮤니티 운영 권한의 의미가 섞인다.

### 근거

- SDD 초안은 `OPS_ADMIN`을 별도 운영 권한으로 둔다.
- 조사 보고서에서 `AuthTokenService`의 roles claim 발급 구조가 구현 전 확인 필요로 분리됐다.
- 신고 검토와 숨김은 사용자 기능이 아니라 운영 권한이므로 beta 권한과 분리해야 한다.

### 영향 범위

- Auth token 발급 서비스.
- JWT 인증 필터와 security config.
- User entity/repository 또는 별도 role mapping entity/repository.
- beta invitation redeem service.
- 관리자 API 인가 테스트.
- `/auth/me` 또는 프로필 응답에 role/beta 표시가 필요하면 API 계약 변경.

### 검증 방법

- 일반 로그인 사용자의 JWT에 `ROLE_OPS_ADMIN`이 없음을 확인한다.
- `OPS_ADMIN` 사용자 JWT에 `ROLE_OPS_ADMIN`이 포함됨을 확인한다.
- beta 미부여 사용자는 복사/반응/신고/팟 참여 API에서 거부된다.
- beta 부여 사용자는 같은 API를 통과한다.
- `OPS_ADMIN`만 신고 검토와 숨김 API를 통과한다.
- 기존 health/monitor 권한 테스트가 깨지지 않는지 확인한다.

### 남은 리스크

- 기존 JWT가 roles claim을 포함하지 않는 경우 프론트 재로그인 또는 refresh 정책이 필요하다.
- beta invitation code를 plain text로 유지할지 hash 저장으로 바꿀지 결정이 필요하다.
- 기존 사용자에게 beta 권한을 소급 부여하는 운영 절차가 필요할 수 있다.

### 후속 구현 전 확인사항

- `user_roles` 테이블명, PK/FK 이름, unique 제약 이름.
- role enum 값의 정확한 저장 문자열.
- 기존 가입자가 초대코드를 입력해 beta 권한을 얻는 API를 만들지 여부.
- `/auth/me` 응답에 `roles`, `betaAccessGranted`를 추가할지 여부.

## 4. ADR-2 Course publication/sourceDetached

### 문제

현재 Course 구조에는 `sourceRideRecordId`가 있고, 주행 기록 삭제 시 Course는 삭제하지 않고 source 연결만 분리하는 정책이 있다. 그러나 `sourceRideRecordId == null`만으로는 처음부터 원본 RideRecord가 없던 Course와, 원본이 있었지만 삭제되어 분리된 Course를 구분할 수 없다.

또한 SDD 초안은 공개 Course, 복사, 카운터, 신고/관리 상태를 원본 Course와 분리해 다루는 방향이다. 기존 `courses.visibility`만으로 커뮤니티 공개 상태, 운영 숨김, 반응/복사/신고 집계를 모두 표현하면 책임이 과하게 섞인다.

### 결정

- 공개 커뮤니티 단위는 `course_publications`로 분리한다.
- 원본 `courses`는 사용자의 실제 Course 자산과 경로 데이터의 기준으로 유지한다.
- `course_publications`는 공개 상태, 공개 시각, 공개 제목/요약 후보, 카운터, moderation status 같은 커뮤니티 메타데이터를 가진다.
- 공개 Course 복사 API는 `courseId`가 아니라 `publicationId` 기준으로 동작한다.
- 복사 시 새 `courses` row를 만들고, `course_copies`에 `publication_id`, 원본 course, 복사된 course, 복사한 사용자를 기록한다.
- `sourceDetached`는 응답 전용 계산값이 아니라 명시적인 영속 필드로 둔다.
- 권장 필드명은 `courses.source_detached BOOLEAN NOT NULL DEFAULT FALSE`다.
- `RideRecord` 삭제로 기존 source 연결을 끊을 때 `source_ride_record_id = NULL`, `source_detached = TRUE`로 갱신한다.
- 처음부터 source가 없는 AI 생성 Course나 수동 Course는 `source_ride_record_id = NULL`, `source_detached = FALSE`다.
- public list/detail 응답은 `sourceDetached`를 Course 또는 publication projection에서 명확히 제공한다.

### 대안

- `courses.visibility`만 사용: 구현은 작지만 publication 카운터, 신고/관리 상태, 복사 정책이 Course 본체에 섞인다.
- `sourceRideRecordId == null`만 사용: 원본이 없던 Course와 원본이 삭제된 Course를 구분하지 못한다.
- publication을 Course와 완전히 분리된 route snapshot으로 저장: 독립성은 높지만 경로 데이터 중복과 migration 부담이 크다.

### 근거

- SDD 초안은 `course_publications`와 `course_copies`를 후보 테이블로 둔다.
- 조사 보고서에서 기존 Course에 `visibility`, `reportHidden`, `sourceRideRecordId`가 있으나 publication 전용 책임은 없다고 정리했다.
- DELETE 계약은 Course를 삭제하지 않고 source 연결만 분리해야 한다.

### 영향 범위

- Course entity와 migration.
- RideRecord 삭제 서비스의 detach 갱신 로직.
- Course publication service/controller.
- public Course list/detail DTO.
- Course copy service.
- 기존 Course 목록 API와 public Course 목록 API의 책임 분리.

### 검증 방법

- source RideRecord가 있는 Course에서 RideRecord 삭제 후 Course가 유지되고 `sourceDetached=true`가 되는지 확인한다.
- 처음부터 source가 없는 Course는 `sourceDetached=false`로 남는지 확인한다.
- `publicationId` 기준 복사 시 새 Course가 생성되고 원본 Course가 변경되지 않는지 확인한다.
- publication 삭제 또는 비공개 처리와 원본 Course 삭제가 서로 다른 동작임을 테스트한다.

### 남은 리스크

- 이미 존재하는 Course의 `source_detached` backfill 기준이 필요하다.
- 공개 후 원본 Course가 수정될 때 publication이 자동 갱신되는지, 명시 갱신되는지 세부 정책이 더 필요하다.
- public detail에서 route point를 원본 Course에서 읽을지, publication snapshot을 둘지 장기 결정이 남아 있다.

### 후속 구현 전 확인사항

- `course_publications`의 정확한 상태 enum.
- publication 생성 시 공개 제목/설명을 Course에서 복사할지 별도 입력받을지.
- owner가 Course를 삭제할 때 publication을 어떻게 처리할지.
- 기존 `courses.reportHidden`과 신규 moderation status의 전환 방식.

## 5. ADR-3 Course report/moderation

### 문제

현재 조사 보고서 기준으로 기존 `course_reports`와 신고 자동 숨김 정책이 존재한다. 하지만 SDD 초안은 신고 접수 후 관리자 검토를 거치며, 관리자 숨김 상태일 때만 공개 목록에서 제외하는 정책을 선택했다.

자동 숨김을 그대로 유지하면 신고 누적만으로 공개 목록에서 사라질 수 있어 SDD 정책과 충돌한다. 반대로 신고 상태만 저장하고 관리자 검토 이력을 남기지 않으면 운영 감사와 포트폴리오 설명 근거가 약해진다.

### 결정

- 커뮤니티 신고는 publication 기준으로 접수한다.
- 기존 `course_reports`는 재사용하되, 커뮤니티 flow에서는 `publication_id`를 기준으로 쓰는 방향을 우선한다.
- 신고 접수는 즉시 숨김 처리하지 않는다.
- publication의 현재 노출 상태는 `course_publications.moderation_status`에 저장한다.
- 관리자 검토 이력은 `course_moderations`에 별도로 남긴다.
- 공개 목록은 `moderation_status = HIDDEN`인 publication만 제외한다.
- report status enum 후보는 다음을 기본으로 한다.
  - `RECEIVED`
  - `UNDER_REVIEW`
  - `RESOLVED`
  - `REJECTED`
  - `DUPLICATE`
- publication moderation status enum 후보는 다음을 기본으로 한다.
  - `VISIBLE`
  - `HIDDEN`
- moderation action enum 후보는 다음을 기본으로 한다.
  - `HIDE`
  - `RESTORE`
  - `MARK_REVIEWED`
- 기존 자동 숨김 로직은 첫 community PR에서 무리하게 삭제하지 않는다. 신규 community report API가 자동 숨김을 타지 않도록 분리하고, legacy report API 전환은 별도 PR로 분리한다.

### 대안

- 기존 자동 숨김 유지: 구현량은 적지만 SDD의 관리자 검토 정책과 충돌한다.
- publication에 `hidden` boolean만 저장: 조회는 쉽지만 검토 이력과 감사 근거가 부족하다.
- 기존 `course_reports`를 버리고 새 report table 생성: 설계는 깨끗하지만 기존 코드와 migration 영향이 커진다.

### 근거

- SDD 초안과 결정 로그는 신고 접수만으로 목록 제외하지 않고 관리자 숨김 상태만 제외한다고 정했다.
- 조사 보고서에서 현재 자동 숨김 정책은 후속 ADR 필요 충돌점으로 분리됐다.
- 운영 기능은 신고 원문, 검토자, 검토 시각, 조치 사유를 추적할 수 있어야 한다.

### 영향 범위

- `course_reports` migration과 repository.
- 신규 `course_moderations` migration/repository/service.
- public Course list filter.
- admin report review API.
- 기존 Course report API와 신규 publication report API의 공존 또는 전환 정책.

### 검증 방법

- 신고 접수 후 publication이 공개 목록에 계속 보이는지 확인한다.
- `OPS_ADMIN`이 `HIDE` 조치한 뒤 공개 목록에서 제외되는지 확인한다.
- `RESTORE` 조치 후 다시 공개 목록에 보이는지 확인한다.
- moderation history가 누적되고 기존 이력이 삭제되지 않는지 확인한다.
- 비관리자 사용자가 moderation API를 호출하면 403인지 확인한다.

### 남은 리스크

- 기존 자동 숨김 API와 신규 moderation 정책이 일정 기간 공존할 수 있다.
- 신고 중복 기준을 사용자당 publication 1회로 할지, 사유별 1회로 할지 최종 확정이 필요하다.
- 신고 사유 enum을 기존 enum으로 재사용할지 SDD용 enum을 확장할지 확인이 필요하다.

### 후속 구현 전 확인사항

- legacy `course_reports.course_id`와 신규 `publication_id`의 공존 migration 전략.
- admin review 화면이 요구하는 필터와 정렬.
- 숨김된 publication detail 접근 시 404, 403, 관리자만 조회 중 무엇으로 할지.
- reportCount를 신고 접수 기준으로 올릴지 유효 신고 기준으로 올릴지.

## 6. ADR-4 공개 Course 목록 조회 성능

### 문제

공개 Course 목록은 최신순, 인기순, 거리순, `likedByMe`, `bookmarkedByMe`, 카운터를 포함해야 한다. 이를 Entity graph와 lazy loading에 맡기면 Course, publication, reaction, report, copy 조회가 row마다 발생해 N+1이 생길 수 있다.

또한 공개 목록은 사용자에게 반복 호출되는 API이고, 관리자 목록은 운영 필터와 page/size가 필요하다. 두 목록의 pagination 방식과 projection 전략을 분리해야 한다.

### 결정

- 공개 목록은 entity 직접 반환이 아니라 projection 또는 read model 기반으로 조회한다.
- 공개 목록은 cursor pagination을 사용한다.
- 관리자 목록은 page/size pagination을 사용한다.
- 최신순 cursor 기준은 `published_at DESC, id DESC`다.
- 인기순 cursor 기준은 `like_count DESC, copy_count DESC, bookmark_count DESC, id DESC`다.
- 거리순은 요청 좌표가 있을 때만 허용한다. 좌표 없이 거리순 요청이 오면 400으로 거부한다.
- 거리순은 PostGIS 거리 계산을 사용할 수 있도록 publication 또는 Course 시작점 geometry 인덱스를 전제로 한다.
- `likedByMe`, `bookmarkedByMe`는 인증 사용자인 경우 현재 page의 `publicationId` 목록을 기준으로 bulk 조회하거나 left join으로 한 번에 계산한다.
- 게스트의 `likedByMe`, `bookmarkedByMe`는 항상 false다.
- `likeCount`, `bookmarkCount`, `copyCount`, `reportCount`는 `course_publications`에 저장된 카운터를 읽는다.
- 카운터는 반응/복사/신고 트랜잭션에서 즉시 증감하고, 후속 배치 보정은 별도 개선으로 둘 수 있다.
- unique 제약 후보는 다음을 기본으로 한다.
  - `course_reactions(publication_id, user_id, reaction_type)`
  - `course_reports(publication_id, reporter_user_id)`
  - `course_copies(copied_course_id)`
- 인덱스 후보는 다음을 기본으로 한다.
  - public latest: `(publication_status, moderation_status, published_at DESC, id DESC)`
  - public popular: `(publication_status, moderation_status, like_count DESC, copy_count DESC, bookmark_count DESC, id DESC)`
  - reaction lookup: `(user_id, reaction_type, publication_id)`
  - report admin: `(status, created_at DESC, id DESC)`
  - distance sort: 시작점 geometry GiST index

### 대안

- Entity + fetch join 중심 목록: 구현은 익숙하지만 반응/카운터/거리순이 붙을수록 중복 row와 N+1 위험이 커진다.
- 매 요청마다 reaction/report/copy count를 집계: 정합성은 높지만 목록 응답 비용이 커진다.
- 공개 목록도 offset page 사용: 구현은 쉽지만 최신 데이터 삽입 시 중복/누락 가능성이 있다.

### 근거

- 기존 조사 보고서에서 Course 목록은 cursor와 `course_list_summaries` read model 구조가 존재한다고 정리됐다.
- SDD 초안은 public list cursor와 admin page/size를 분리했다.
- 포트폴리오 목적상 단순 기능 구현보다 N+1 방지, read model, 인덱스, 부하테스트 기준을 명확히 설명할 수 있어야 한다.

### 영향 범위

- `course_publications` schema.
- `course_reactions`, `course_copies`, `course_reports` schema.
- public Course list repository/projection.
- admin Course/report list repository.
- 카운터 증감 트랜잭션.
- query-count 테스트와 k6 smoke 시나리오.

### 검증 방법

- 인증 사용자 public list 조회 시 query count가 고정 범위 안에 있는지 확인한다.
- 20개 publication 목록에서 `likedByMe`, `bookmarkedByMe` 계산이 row별 조회로 늘어나지 않는지 확인한다.
- cursor pagination에서 다음 페이지 중복/누락이 없는지 확인한다.
- 거리순 요청에 좌표가 없으면 400을 반환하는지 확인한다.
- 로컬 k6 smoke 후보 기준으로 public list p95 목표를 잡고 회귀 측정한다.

### 남은 리스크

- H2 테스트와 PostGIS 거리순 쿼리의 차이가 커서 실제 Postgres 통합 테스트가 필요하다.
- 카운터 즉시 증감은 동시성 충돌 가능성이 있어 optimistic update 또는 DB atomic update 기준을 정해야 한다.
- 거리순은 데이터량이 커지면 별도 캐시나 근처 후보군 제한이 필요할 수 있다.

### 후속 구현 전 확인사항

- public list page size 기본값과 최대값.
- 인기순의 정확한 가중치. MVP는 정렬 우선순위로 충분한지, 점수식을 둘지 결정 필요.
- 거리순 요청 좌표 파라미터명.
- query-count 테스트에 사용할 테스트 도구와 기준 수치.
- k6 smoke 기준. 예: 로컬 의존성 기준 100 VU 혼합 시나리오, public list p95 목표, 오류율 목표.

## 7. ADR 간 의존성

- ADR-1은 모든 커뮤니티/팟 mutation API의 선행 조건이다. beta와 `OPS_ADMIN` 경계가 닫히기 전에는 신고 검토, 복사, 팟 참여 API를 구현하면 안 된다.
- ADR-2는 ADR-3과 ADR-4의 데이터 기준이다. `course_publications`가 없으면 publication 기준 신고, 복사, 목록 카운터가 흔들린다.
- ADR-3은 ADR-4의 공개 목록 필터와 직접 연결된다. `moderation_status=HIDDEN` 조건이 목록 필터에 들어가야 한다.
- ADR-4는 ADR-2의 publication 카운터와 ADR-3의 report/moderation status를 읽는 조회 전략이다.

## 8. 후속 구현 순서 추천

1. 권한 기반 공통 준비: `user_roles`, JWT roles claim, beta guard, `OPS_ADMIN` 인가 테스트.
2. Course source detach 보강: `source_detached` migration, 기존 RideRecord delete detach 테스트 보강.
3. Course publication MVP: publication 생성/비공개/조회 기준과 `publicationId` 도입.
4. Reaction/copy/report 저장 구조: `course_reactions`, `course_copies`, publication 기준 `course_reports`.
5. Moderation flow: `course_moderations`, 관리자 숨김/복구, 공개 목록 필터.
6. Public list 성능: projection/read model, cursor, `likedByMe`/`bookmarkedByMe` bulk 조회, 인덱스.
7. Pot 도메인: 위 권한 체계가 닫힌 뒤 `ride_pots`, `ride_pot_members`, `ride_pot_events` 구현.

## 9. 구현 프롬프트 작성 시 금지/주의사항

- 이 ADR만 보고 한 번에 커뮤니티/팟 전체를 구현하라고 지시하지 않는다.
- `1 API = 1 PR` 원칙을 우선하고, migration도 기능 단위로 작게 나눈다.
- `course_publications`, `course_reactions`, `course_reports`, `course_moderations`를 한 PR에 모두 넣지 않는다.
- 기존 자동 숨김 로직을 삭제하는 작업과 신규 moderation 도입을 같은 PR에 섞지 않는다.
- API 계약이 없는 DTO 필드는 구현자가 임의로 만들지 않는다.
- 거리순, 인기순, 카운터 보정, no-show 제재 같은 확장 정책은 MVP 구현에 끼워 넣지 않는다.
- H2만 통과한 거리순/PostGIS 쿼리를 운영 검증 완료로 쓰지 않는다.
- 민감정보, JWT secret, 외부 API key를 보고서나 테스트 로그에 남기지 않는다.

## 10. 포트폴리오에 써도 되는 표현

- "커뮤니티 기능 도입 전 기존 Course, 신고, 인증 구조와 충돌하는 지점을 조사하고 ADR로 분리했다."
- "공개 Course 목록의 N+1 위험을 줄이기 위해 publication/read model/projection 기반 조회 전략과 cursor pagination을 설계했다."
- "신고 즉시 자동 숨김 대신 관리자 검토 이력을 남기는 moderation 구조로 운영 감사 가능성을 고려했다."
- "주행 기록 원본 삭제와 공개 Course 유지 정책을 분리하기 위해 `sourceDetached`를 명시 상태로 설계했다."

## 11. 과장하면 안 되는 표현

- "커뮤니티/팟 기능을 구현 완료했다."
- "운영 환경에서 성능 개선이 검증됐다."
- "신고/관리자 기능이 배포 가능하다."
- "N+1 문제가 실제 운영 데이터에서 해결됐다."
- "OPS_ADMIN 권한 체계가 코드에 적용됐다."
